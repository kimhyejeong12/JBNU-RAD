# 권한 DB 스키마 설계 (검토용)

## 0. 결정 사항 (2026-10-11, 양현성)

1. **권한은 3단계 결재를 기반으로 만든다.**
   | 역할 | 하는 일 |
   |---|---|
   | 일반 사용자 (`user`) | 권한 신청을 **요청**한다. 1차 결재 전이면 **철회**할 수 있다 |
   | 보안 운영자 (`manager`) | **1차 승인** · 반려. 승인하면 보안 총책임자에게 올라간다 |
   | 보안 총책임자 (`top`) | **최종 승인** · 반려. 승인된 권한을 **회수**한다 |
   - 업무 절차서의 흐름(신청자 → 부서장 검토 → 정보보호 담당자 승인)과 대응한다.
2. **루트 = 보안 총책임자 중 한 명, 계정을 만드는 유일한 사람.** 초기 루트는 웹 밖의 별도 방법으로 만든다. 루트가 다른 보안 총책임자 · 보안 운영자 · 일반 사용자를 만든다. 자기 가입은 없다.
3. **감사자(`auditor`) 역할은 없앤다.**
4. **보안 운영자는 어느 부서에든 배치될 수 있다.** 신청자 부서와 상관없이 결재하고, **누가 결재했는지**(이름 · 부서까지) 남긴다.
5. **반려되면 끝이다.** 다시 하려면 새 신청을 낸다.
6. **신청 번호에 날짜를 넣는다.** `REQ-YYYYMMDD-NNN` (예: `REQ-20261011-001`).
7. **비밀번호는 가장 안전한 해시로.** → Argon2id (§2 `users`).
8. **세션은 2일.**
9. **화면을 권한 관리 전반으로 넓힌다.** 승인 · 반려만이 아니라 회수(revoke)까지. 지금 대시보드는 보안 운영자용으로 두고, 보안 총책임자용을 따로 만든다 (§3).
10. **DB를 나눈다 — AI가 만든 것은 Log DB, 사람이 한 것은 권한 DB** (10/12 정리). 권한 DB(이 문서) = 사용자 · 인증 · 감사 기록 · 신청 · 결재 · 회수 · 운영자 결정. Log DB(→ AI 결과 DB, [`results-db.md`](results-db.md)) = AI 판정(정책 관리 검토 · 로그 감시) · 질의 기록 · 보안 솔루션 로그. 권한 신청 AI 판정은 예외로 권한 DB (결정 16).
11. **(4차) 해시는 RFC 9106 권장 2** (Argon2id 64 MiB · t=3 · p=4, 로그인 약 50 ms).
12. **(4차) 보안 운영자도 회수할 수 있다.** 활성 보안 운영자 · 보안 총책임자 누구나 (자기가 1차 승인한 건으로 한정하지 않음 — 가정, §5).
13. **(4차) AI 판정은 신청이 들어오는 즉시** 백그라운드로 돌려 남긴다 (6차부터 신청 행의 AI 칸). 실패하거나 웹이 꺼지는 사이에 못 끝낸 판정은 다음 시작 때 다시 돈다.
14. **(5차) 정책 관리 · 로그 감시의 운영자 결정도 권한 DB에 남긴다** (`review_decisions`). 사람의 결정이라 결정자(사용자)와 같은 DB에 둔다.
15. **(6차, 10/12) 권한 신청 1건 = 1행.** 신청 행에 확인 칸 세 묶음 — **AI 판정 · 1차(보안 운영자) 결재 · 최종(보안 총책임자) 결재** — 을 두고 각 판단 결과와 함께 저장한다. 승인된 권한의 기록은 이 행 하나로 충분하다. `approvals` · `revocations` 테이블과 Log DB의 `request_verdicts`는 없앤다 (회수도 같은 행의 칸).
16. **(6차) 권한 신청 AI 판정은 권한 DB에 둔다.** 보안 총책임자까지 올라가는 결재 근거라서, Log DB 정리와 상관없이 신청과 함께 남아야 한다. 권한 DB를 계정과 신청으로 나누지 않는다 — 결재 순서 · 역할을 강제하는 트리거가 `users`를 봐야 하는데, SQLite 트리거는 다른 DB 파일을 볼 수 없다.
17. **(6차) AI 판정은 1차 결재 전까지만 바뀐다.** 다시 판정하면 덮어쓴다. 보안 운영자가 결재하면 AI 칸이 굳어서, 보안 총책임자는 보안 운영자가 본 판정을 그대로 본다. 결재 때 판정이 아직 없었거나 실패했으면 "AI 판정 없이 결재"로 남고, 그 뒤에 끝난 판정은 버린다.
18. **(7차, 10/12) 보안 총책임자 화면 = 보안 운영자 화면 + 계정 관리, 계정 관리는 보안 총책임자부터.** 보안 총책임자도 정책 관리 · 로그 감시를 보고, 아래에서 올라온 판단(정책 · 로그 결정 기록 전부 — 취소 · 의견 포함, 권한 신청은 1차 결재 의견)을 읽는다. 계정 생성 · 수정 · 비밀번호 초기화는 활성 보안 총책임자 누구나 (`accounts.sql`이 트리거를 바꾼다). 루트 계정은 루트만 고친다 — 다른 보안 총책임자가 루트 비밀번호를 초기화하면 루트를 가로챌 수 있다. 자기 역할 · 활성은 바꿀 수 없다 (실수로 계정 관리에서 밀려나지 않게).

## 1. 무엇을 바꾸나

| 지금 | 바뀐 뒤 |
|---|---|
| 권한 신청 = CSV 파일 (지금은 지워져 없음) | 일반 사용자가 화면에서 신청 → DB |
| 승인 · 반려 = 브라우저 메모리, 새로고침하면 사라짐 | 1차 · 최종 결재와 회수가 DB에 남는다. 고치거나 지울 수 없다 |
| 정책 · 로그 결정 = 브라우저 메모리 | 결정 · 취소가 DB에 쌓인다 (`review_decisions`) |
| 로그인 없음 | ID/PW 로그인(Argon2id · 세션 2일), 역할 3개, 보안 총책임자가 계정 생성 (처음엔 루트만, 10/12에 넓힘), 감사 기록 |

- SQLite (파일 하나, 서버 불필요, 표준 라이브러리). WAL 모드.
- 데이터 계층 · 판정 흐름(`engine/pipeline.py`)은 DB를 모른다. `sentinelai/db/`는 `Engine`(engine.py — 10/20에 작업 큐와 함께 옮겼다)과 `web`이 쓴다.
- **결재 규칙은 DB가 강제한다 (트리거).** 화면 · 앱 코드에 버그가 있어도 순서를 건너뛰거나, 역할이 아닌 사람이 결재 · 회수하거나, 기록을 고칠 수 없다.
- 시각은 ISO 8601 UTC 문자열. 값은 문자열 위주, 필수 칸 최소.
- 추가 패키지: `argon2-cffi` 하나.

## 2. 테이블

```
users ─┬─ sessions
       ├─ audit_log
       └─ access_requests (신청자 · AI 판정 · 1차 결재자 · 최종 결재자 · 회수자 — 한 행)
users ── review_decisions (정책 관리 · 로그 감시 결정, 결정자)
```

- 스키마 파일은 차례로 적용한다 (`Database(path, "schema.sql", "decisions.sql", "accounts.sql", "decisions_server.sql", "roles_names.sql", "nodes.sql", "nodes_keys.sql")`). n번째 파일을 적용하면 `user_version = n`. 이미 만든 DB는 시작할 때 빠진 파일만 더 적용한다. 테이블을 더할 때는 새 파일을 뒤에 붙이고, 앞 파일은 고치지 않는다.

### 신청의 상태 (`access_requests.stage`)

```
             ┌─ 철회 (신청자) ──────────────────────▶ withdrawn
             │
 신청 ──▶ manager ──1차 승인──▶ top ──최종 승인──▶ approved ──회수 (보안 총책임자)──▶ revoked
             │                    │
             └─ 반려 ─────────────┴─ 반려 ─────────▶ rejected      (반려 · 철회 뒤에는 새 신청)
```

- 이 화살표 말고는 상태가 바뀌지 않는다 (트리거 `access_requests_stage_path`).
- 결재 · 회수 칸을 채우면 DB가 상태를 바꾼다. 앱은 상태를 직접 승인 · 회수로 바꾸지 않는다 (철회만 앱이 바꾼다).
- 제출한 신청 내용(권한 · 사유 · 기간 등)과 한 번 채운 결재 · 회수 칸은 고칠 수 없다. AI 칸은 1차 결재 전까지만 바뀐다. 행은 지울 수 없다.
- 지금 쓸 수 있는 권한 = `active_grants` 뷰: 승인됐고, 회수되지 않았고, 사용 기간이 안 끝난 것.

### `users`
| 칸 | 설명 |
|---|---|
| `login_id` | 로그인 ID. 대소문자 구분 없이 유일 |
| `password_hash` | **Argon2id** PHC 문자열 (`$argon2id$v=19$m=…,t=…,p=…$솔트$해시`). 비용 값이 문자열에 들어 있어 나중에 올려도 기존 해시를 읽을 수 있고, 로그인할 때 새 비용으로 다시 해시한다 |
| `department` | 소속 부서. 보안 운영자의 배치 부서 |
| `role` · `is_root` | `top` · `manager` · `user`. 루트는 **한 명**, 반드시 `top`, 만든 사람이 비어도 되는 유일한 계정 |
| `created_by` | 만든 사람. **활성 루트여야 한다** (트리거) |
| `is_active` | 정지 · 퇴사. 행은 지우지 않는다 (결재 기록이 가리킨다). 정지되면 결재 · 회수 · 신청 못 함 |
| `must_change_password` | 루트가 만들거나 초기화한 계정은 첫 로그인에 바꾸게 한다 |
| `failed_logins` · `locked_until` | 연속 실패 시 잠금 |

**Argon2id 비용** (이 PC에서 측정):
| 설정 | 메모리 | 해시 1회 |
|---|---|---|
| RFC 9106 권장 1 | 2 GiB | 0.9초 |
| **RFC 9106 권장 2 (기본안)** | **64 MiB** | **49 ms** |

권장 1이 더 강하지만 로그인 1회에 2 GiB를 쓴다. 팀 서버(RAM 31 GB)는 LLM과 함께 쓰므로 동시 로그인 몇 건으로 메모리가 바닥날 수 있다. 그래서 기본안은 권장 2 + 로그인 잠금 — §4 질문 1.

### `sessions` — 2일
브라우저에는 무작위 토큰을 HttpOnly · Secure · SameSite=Strict 쿠키로 주고, DB에는 **토큰 해시만** 둔다. `expires_at` = 로그인 + 2일. 로그아웃 · 비밀번호 변경 · 정지 시 `revoked_at`.

### `audit_log`
로그인 성공 · 실패, 로그아웃, 계정 생성 · 변경 · 정지 · 비밀번호 초기화, 신청, 철회, 결재, 회수.

### `access_requests`
| 칸 | 설명 |
|---|---|
| `request_no` | `REQ-YYYYMMDD-NNN`. 형식과 **실제 있는 날짜**인지 DB가 검사한다 (13월 · 2월 30일 거부, 윤년 2월 29일 허용). 번호는 앱이 그날 마지막 번호 + 1로 만든다 (하루 999건까지) |
| `requester_id` | 신청자. **활성 일반 사용자만** (트리거) |
| `requester_name` · `requester_department` | 신청 당시 사본 |
| `access_code` | 신청한 권한 — 권한 목록(`access_catalog`)의 **켜진** 코드만 (트리거, `access_catalog.sql` 10/20). 그 전 신청은 비어 있다 |
| `requested_access` · `current_access` | 신청 권한 이름(신청 당시 목록 이름의 사본 — 목록 이름이 바뀌어도 기록은 그대로) · 신청 때 보유 권한. AI 판정(`review_chain`) 입력 — 신청 권한에는 목록의 코드 · 시스템 · 분류 · 설명을 붙여 넘긴다 |
| `reason` · `period_start` · `period_end` | 신청 사유 · 사용 기간 (절차서 3단계 "신청 사유, 사용 기간 등 타당성 검토") |
| `stage` · `closed_at` | 위 상태도. 승인 완료 · 반려 · 철회 · 회수 시각 |

확인 칸 세 묶음 — 각 판단과 그 결과를 함께 둔다.

| 묶음 | 칸 | 채우는 때 · 규칙 |
|---|---|---|
| **AI 판정** | `ai_level` · `ai_reason` · `ai_recommendation` · `ai_sources`(JSON) · `ai_failed` · `ai_error` · `ai_model` · `ai_elapsed_sec` · `ai_judged_at` | 신청 즉시 백그라운드로. 다시 판정하면 덮어씀. **1차 결재 뒤에는 바꿀 수 없다** (트리거). AI는 권고만 한다 — 이 칸은 상태를 바꾸지 않는다 |
| **1차 결재** | `manager_action`(`approve` · `reject`) · `manager_comment` · `manager_id` + `manager_name` · `manager_department` · `manager_decided_at` | 상태가 `manager`일 때 한 번. **활성 보안 운영자만** (트리거). 승인 → `top`, 반려 → `rejected` |
| **최종 결재** | `top_action` · `top_comment` · `top_id` + `top_name` · `top_department` · `top_decided_at` | 상태가 `top`일 때 한 번. **활성 보안 총책임자만**. 승인 → `approved`, 반려 → `rejected` |
| 회수 | `revoke_reason`(필수) · `revoker_id` + `revoker_name` · `revoker_department` · `revoked_at` | `approved`일 때 한 번. **활성 보안 운영자 · 보안 총책임자** → `revoked` |

- 결재자 · 회수자 이름 · 부서는 그때 사본이다 (결정 4).
- 결재자가 본 AI 판정 = 그 행의 AI 칸 (결정 17로 1차 결재 뒤 굳는다). 따로 참조값 · 등급 사본을 두지 않는다.
- 판정 실패 · 재시도 이력은 남기지 않는다 (마지막 판정만). 실패 원인은 서버 로그에 남는다.

### `review_decisions` — 정책 · 로그 결정 1건 = 1행 (`decisions.sql`)
| 칸 | 설명 |
|---|---|
| `kind` | `policy`(정책 관리 문제) · `server`(서버 점검, 10/12 `decisions_server.sql`이 표를 다시 만들어 넓혔다) · `event`(로그 감시 판정) |
| `item_key` | 결정한 항목. 로그 감시 = 판정 id(`사용자@마지막 로그 시각`, 감시 결과가 쌓여도 그대로). 정책 = `실행 시각#순번` — 정책 검토는 돌릴 때마다 문제 목록을 새로 만들므로, 다시 돌리면 예전 결정은 새 문제에 붙지 않는다 |
| `subject` | 결정할 때 화면에 보인 대상 (정책 ID · 문제 유형, 로그 사용자) — 결과 파일이 바뀌어도 무엇을 결정했는지 남긴다 |
| `action` | 정책: `approve` · `cond` · `reject`, 서버 · 로그: `clear` · `act`, 모두 `cancel`(취소) |
| `comment` · `ai_level` | 결정 의견(선택) · 그때 AI 등급 |
| `decider_id` + `decider_name` · `decider_department` | 결정자와 당시 사본. **활성 보안 운영자 · 보안 총책임자만** (트리거) |

- 고치거나 지울 수 없다. 항목마다 마지막 기록이 지금 결정이고, 마지막이 `cancel`이면 결정이 없는 것이다.

## 3. 화면 (권한 관리) — 구현됨 (결재 이력 화면은 따로 두지 않고 결재함 [전체] · 패널의 결재 기록으로 대신)

| 화면 | 누가 | 하는 일 |
|---|---|---|
| 로그인 · 비밀번호 변경 | 모두 | 첫 로그인이면 비밀번호부터 바꾼다 |

## 4. 검증한 것 (`schema.sql`을 SQLite로 실행)

루트 → 보안 총책임자 · 보안 운영자 2명(영업팀 · 인사팀) · 일반 사용자를 만들고 돌려 봤다.

- 신청 → 인사팀 보안 운영자 1차 승인 → 다른 보안 총책임자 최종 승인 → `approved`. 결재자 이름 · 부서 · AI 등급이 남는다.
- 보안 운영자 반려 → `rejected`. 1차 결재 전 철회 → `withdrawn`.
- 보안 총책임자 회수 → `revoked`, `active_grants`에서 빠진다. 회수자 이름 · 부서 · 사유가 남는다.
- 아래 **25가지**를 DB가 거부한다.
  - 계정: 루트 아닌 사람의 계정 생성(보안 총책임자 · 보안 운영자), 루트 두 명, 만든 사람 없는 계정, 루트를 보안 총책임자 아닌 역할로, 감사자 역할
  - 신청: 보안 운영자의 신청, 날짜 없는 번호, 13월 번호, 2월 30일 번호, 제출한 내용 고치기
  - 결재: 1차를 건너뛴 최종 승인, 일반 사용자 · 보안 총책임자의 1차 결재, 같은 단계 두 번, 반려된 신청에 결재, 정지된 보안 운영자의 결재, 결재 기록 수정 · 삭제
  - 상태: 1차 승인 뒤 철회, 반려된 신청 되살리기, 결재 없이 승인 완료로 바꾸기
  - 회수: 보안 운영자의 회수, 승인 안 된 신청 회수, 두 번 회수, 회수 기록 삭제

## 권한 목록 `access_catalog` (10/20, `access_catalog.sql`)

일반 사용자는 이 목록에 있는 권한만 신청한다. 그 전에는 신청 권한을 자유 입력으로 받아 같은 권한이 신청마다 다르게 적혔다 (유효 권한 · 회수를 권한별로 모을 수 없었다). 목록에 없는 권한은 신청하지 않는다 — 필요하면 보안 총책임자에게 등록을 요청한다 (10/20 결정).

| 칸 | 설명 |
|---|---|
| `code` | 권한 코드 (영문 · 숫자 · `_ . -` 1~64자, 한 번만). **바꿀 수 없다** (트리거) — 지난 신청이 가리킨다 |
| `name` · `system` · `category` · `description` | 이름(필수) · 시스템 · 분류(인사정보 · 급여정보 · 관리자 등, 정해 둔 값 없음) · 설명. 분류 · 설명은 AI 판정 입력에 붙어 조항 검색의 실마리가 된다 (10/20 시험: 급여정보 → 3.3 · 4.2 위험) |
| `is_active` | 끄면 새 신청만 막는다. 결재 중인 신청 · 받은 권한은 그대로 |
| `created_by` · `created_at` · `updated_at` | 등록한 보안 총책임자(트리거가 확인) · 시각 |

**현재 보유 권한은 신청자가 적지 않는다** (10/20). 신청할 때 서버가 그 사람의 최종 승인 · 사용 기간이 남은 신청(회수 · 만료 제외, 날짜는 서버 현지 날짜)을 읽어 `current_access`에 "이름 (코드) — 기간" 줄로 남긴다 — AI 판정과 결재자가 본 그대로가 기록에 남고, 나중에 회수돼도 신청 행은 바뀌지 않는다. 이미 가진 권한 · 결재 중인 같은 권한은 다시 신청할 수 없다. 이 시스템 밖에서 받은 권한(도입 전부터 가진 권한)은 아직 읽을 곳이 없다 — 받으려면 계정별 기본 권한을 따로 넣는 곳이 필요하다 (남은 질문 11).

지우지 않는다 (트리거). 등록 · 고치기는 감사 기록(`access_create` · `access_update`)에 남는다. 목록 출처(IAM · 자산관리 내보내기 읽기)는 아직 없다 — 화면에서 보안 총책임자가 넣는다.

## 수집 노드 등록부 `nodes` (10/20, `nodes.sql`)

| 칸 | 설명 |
|---|---|
| `name` | 노드 이름 (영문 · 숫자 · `. _ -` 1~64자, 한 번만) |
| `key_hash` · `key` | 노드만의 키의 SHA-256(한 번만, `nodes_keys.sql`의 인덱스로 키 → 노드를 찾는다)과 키 자체(`nodes_key_view.sql` — 내부망 서비스라 화면에서 다시 볼 수 있게 둔다, 10/20. 그 전에 발급한 키는 해시만 있다). 키는 32바이트 무작위 값이라 느린 해시가 필요 없다. 비어 있으면(손으로 넣은 수집뿐) 노드가 보낼 수 없다 |
| `host` · `ip` · `agent_version` · `interval_min` | 노드가 마지막으로 보낸 값. 끊김 = `interval_min`의 세 배 넘게 소식 없음 |
| `enabled` | 끄면 보내도 403, 주기 점검에서도 빠진다 |
| `registered_at` · `last_seen_at` · `last_collected_at` | 등록 · 마지막 연락 · 마지막으로 새로 쌓인 수집 시각 |

노드는 화면에서 등록하고(보안 운영자 · 보안 총책임자) 그때 키를 한 번 보여준다. 노드는 이름 없이 키만 보낸다. 처음에는 공용 등록 토큰으로 처음 보낸 노드를 자동 등록했으나(10/20 오전) 같은 날 "메인에서 서버당 키를 발급"으로 바꿨다 — 토큰 하나가 새면 아무 이름이나 등록할 수 있었다. 등록 · 키 발급 · 끄기는 감사 기록(`node_create` · `node_key_issue` · `node_update` · `node_import`)에 남는다.
