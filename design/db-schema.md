# 권한 DB 스키마 설계 (검토용)

SentinelAI — 전북대학교 RAD(RAG & Decision) · SK쉴더스
DDL: [`sentinelai/db/schema.sql`](../sentinelai/db/schema.sql) (권한 DB) · [`log_schema.sql`](../sentinelai/db/log_schema.sql) (Log DB, 신청 판정만) · 2026-10-11 확정 · **DB 계층과 API까지 구현** (화면은 다음 단계)

---

## 0. 결정 사항 (2026-10-11, 양현성)

1. **권한은 3단계 결재를 기반으로 만든다.**
   | 역할 | 하는 일 |
   |---|---|
   | 일반사용자 (`user`) | 권한 신청을 **요청**한다. 1차 결재 전이면 **철회**할 수 있다 |
   | 중간관리자 (`manager`) | **1차 승인** · 반려. 승인하면 최상급자에게 올라간다 |
   | 최상급자 (`top`) | **최종 승인** · 반려. 승인된 권한을 **회수**한다 |
   - 업무 절차서의 흐름(신청자 → 부서장 검토 → 정보보호 담당자 승인)과 대응한다.
2. **루트 = 최상급자 중 한 명, 계정을 만드는 유일한 사람.** 초기 루트는 웹 밖의 별도 방법으로 만든다. 루트가 다른 최상급자 · 중간관리자 · 일반사용자를 만든다. 자기 가입은 없다.
3. **감사자(`auditor`) 역할은 없앤다.**
4. **중간관리자는 어느 부서에든 배치될 수 있다.** 신청자 부서와 상관없이 결재하고, **누가 결재했는지**(이름 · 부서까지) 남긴다.
5. **반려되면 끝이다.** 다시 하려면 새 신청을 낸다.
6. **신청 번호에 날짜를 넣는다.** `REQ-YYYYMMDD-NNN` (예: `REQ-20261011-001`).
7. **비밀번호는 가장 안전한 해시로.** → Argon2id (§2 `users`).
8. **세션은 2일.**
9. **화면을 권한 관리 전반으로 넓힌다.** 승인 · 반려만이 아니라 회수(revoke)까지. 지금 대시보드는 중간관리자용으로 두고, 최상급자용을 따로 만든다 (§3).
10. **DB를 나눈다.** 권한 DB(이 문서) = 사용자 · 인증 · 감사 기록 · 신청 · 결재 · 회수. Log DB(나중에 설계) = AI 판정 · 보안 솔루션 로그 · 로그 감시 판정. 결재 기록에는 결재자가 본 AI 판정의 Log DB 참조값과 그때의 등급만 남긴다.
11. **(4차) 해시는 RFC 9106 권장 2** (Argon2id 64 MiB · t=3 · p=4, 로그인 약 50 ms).
12. **(4차) 중간관리자도 회수할 수 있다.** 활성 중간관리자 · 최상급자 누구나 (자기가 1차 승인한 건으로 한정하지 않음 — 가정, §5).
13. **(4차) AI 판정은 신청이 들어오는 즉시** 백그라운드로 돌려 Log DB에 남긴다. 실패하거나 웹이 꺼지는 사이에 못 끝낸 판정은 다음 시작 때 다시 돈다.

## 1. 무엇을 바꾸나

| 지금 | 바뀐 뒤 |
|---|---|
| 권한 신청 = CSV 파일 (지금은 지워져 없음) | 일반사용자가 화면에서 신청 → DB |
| 승인 · 반려 = 브라우저 메모리, 새로고침하면 사라짐 | 1차 · 최종 결재와 회수가 DB에 남는다. 고치거나 지울 수 없다 |
| 로그인 없음 | ID/PW 로그인(Argon2id · 세션 2일), 역할 3개, 루트만 계정 생성, 감사 기록 |

- SQLite (파일 하나, 서버 불필요, 표준 라이브러리). WAL 모드.
- 엔진 · 데이터 계층은 DB를 모른다. 새 모듈 `sentinelai/db/`를 `pipeline` · `web`만 쓴다.
- **결재 규칙은 DB가 강제한다 (트리거).** 화면 · 앱 코드에 버그가 있어도 순서를 건너뛰거나, 역할이 아닌 사람이 결재 · 회수하거나, 기록을 고칠 수 없다.
- 시각은 ISO 8601 UTC 문자열. 값은 문자열 위주, 필수 칸 최소.
- 추가 패키지: `argon2-cffi` 하나.

## 2. 테이블

```
users ─┬─ sessions
       ├─ audit_log
       └─ access_requests (신청자) ─┬─ approvals   (1차 · 최종 결재, 결재자)   ─ ai_verdict_ref → Log DB
                                     └─ revocations (회수, 회수자)
```

### 신청의 상태 (`access_requests.stage`)

```
             ┌─ 철회 (신청자) ──────────────────────▶ withdrawn
             │
 신청 ──▶ manager ──1차 승인──▶ top ──최종 승인──▶ approved ──회수 (최상급자)──▶ revoked
             │                    │
             └─ 반려 ─────────────┴─ 반려 ─────────▶ rejected      (반려 · 철회 뒤에는 새 신청)
```

- 이 화살표 말고는 상태가 바뀌지 않는다 (트리거 `access_requests_stage_path`).
- 결재 · 회수 기록을 넣으면 DB가 상태를 바꾼다. 앱은 상태를 직접 승인 · 회수로 바꾸지 않는다 (철회만 앱이 바꾼다).
- 제출한 신청 내용(권한 · 사유 · 기간 등)은 고칠 수 없다.
- 지금 쓸 수 있는 권한 = `active_grants` 뷰: 승인됐고, 회수되지 않았고, 사용 기간이 안 끝난 것.

### `users`
| 칸 | 설명 |
|---|---|
| `login_id` | 로그인 ID. 대소문자 구분 없이 유일 |
| `password_hash` | **Argon2id** PHC 문자열 (`$argon2id$v=19$m=…,t=…,p=…$솔트$해시`). 비용 값이 문자열에 들어 있어 나중에 올려도 기존 해시를 읽을 수 있고, 로그인할 때 새 비용으로 다시 해시한다 |
| `department` | 소속 부서. 중간관리자의 배치 부서 |
| `role` · `is_root` | `top` · `manager` · `user`. 루트는 **한 명**, 반드시 `top`, 만든 사람이 비어도 되는 유일한 계정 |
| `created_by` | 만든 사람. **활성 루트여야 한다** (트리거) |
| `is_active` | 정지 · 퇴사. 행은 지우지 않는다 (결재 기록이 가리킨다). 정지되면 결재 · 회수 · 신청 못 함 |
| `must_change_password` | 루트가 만들거나 초기화한 계정은 첫 로그인에 바꾸게 한다 |
| `failed_logins` · `locked_until` | 연속 실패 시 잠금 |

**Argon2id 비용** (이 PC에서 측정):
| 설정 | 메모리 | 해시 1회 |
|---|---|---|
| RFC 9106 권장 1 | 2 GiB | 0.9초 |
| **RFC 9106 권장 2 (기본안)** | **64 MiB** | **49 ms** |

권장 1이 더 강하지만 로그인 1회에 2 GiB를 쓴다. 팀 서버(RAM 31 GB)는 LLM과 함께 쓰므로 동시 로그인 몇 건으로 메모리가 바닥날 수 있다. 그래서 기본안은 권장 2 + 로그인 잠금 — §4 질문 1.

### `sessions` — 2일
브라우저에는 무작위 토큰을 HttpOnly · Secure · SameSite=Strict 쿠키로 주고, DB에는 **토큰 해시만** 둔다. `expires_at` = 로그인 + 2일. 로그아웃 · 비밀번호 변경 · 정지 시 `revoked_at`.

### `audit_log`
로그인 성공 · 실패, 로그아웃, 계정 생성 · 변경 · 정지 · 비밀번호 초기화, 신청, 철회, 결재, 회수.

### `access_requests`
| 칸 | 설명 |
|---|---|
| `request_no` | `REQ-YYYYMMDD-NNN`. 형식과 **실제 있는 날짜**인지 DB가 검사한다 (13월 · 2월 30일 거부, 윤년 2월 29일 허용). 번호는 앱이 그날 마지막 번호 + 1로 만든다 (하루 999건까지) |
| `requester_id` | 신청자. **활성 일반사용자만** (트리거) |
| `requester_name` · `requester_department` | 신청 당시 사본 |
| `requested_access` · `current_access` | AI 판정(`review_chain`) 입력 |
| `reason` · `period_start` · `period_end` | 신청 사유 · 사용 기간 (절차서 3단계 "신청 사유, 사용 기간 등 타당성 검토") |
| `stage` · `closed_at` | 위 상태도. 승인 완료 · 반려 · 철회 · 회수 시각 |

### `approvals` — 결재 1건 = 1행
| 칸 | 설명 |
|---|---|
| `step` · `action` | `manager` · `top` 단계의 `approve` · `reject` |
| `approver_id` + `approver_name` · `approver_department` | 결재자와 **결재 당시 이름 · 부서 사본** (결정 4) |
| `ai_verdict_ref` · `ai_level` | 결재자가 본 AI 판정 (Log DB 참조값 · 등급 사본) |
| `comment` | 결재 의견 |

### `revocations` — 회수 1건 = 1행
| 칸 | 설명 |
|---|---|
| `request_id` | 회수한 신청. 신청당 한 번 |
| `reason` | 회수 사유 (필수) |
| `revoker_id` + `revoker_name` · `revoker_department` | 회수자와 당시 사본. **활성 중간관리자 · 최상급자만** (트리거) |

## 3. 화면 (권한 관리) — 초안

| 화면 | 누가 | 하는 일 |
|---|---|---|
| 로그인 · 비밀번호 변경 | 모두 | 첫 로그인이면 비밀번호부터 바꾼다 |
| **내 신청** | 일반사용자 | 신청서 작성(권한 · 현재 권한 · 사유 · 사용 기간), 내 신청 상태, 1차 결재 전 철회 |
| **결재함 (1차)** | 중간관리자 | `manager` 단계 신청 목록 → 신청 내용 + AI 판정 · 근거를 보고 승인 · 반려(의견). 지금 대시보드(정책 관리 · 로그 감시 메뉴 포함)를 이 사람들이 쓴다 |
| **결재함 (최종)** | 최상급자 | `top` 단계 신청 → 1차 결재자 · 의견 · AI 판정을 보고 최종 승인 · 반려 |
| **권한 현황 · 회수** | 중간관리자 · 최상급자 | `active_grants` 목록(신청자 · 권한 · 기간 · 결재자) → 사유를 적고 회수. 회수 · 만료된 권한 이력 |
| **결재 이력** | 최상급자 (중간관리자는 자기 결재만?) | 신청별 결재 · 회수 기록 — 누가 · 언제 · 어떤 AI 판정을 보고 |
| **계정 관리** | 루트 | 계정 생성 · 역할 · 부서 · 정지 · 비밀번호 초기화 |

## 4. 검증한 것 (`schema.sql`을 SQLite로 실행)

루트 → 최상급자 · 중간관리자 2명(영업팀 · 인사팀) · 일반사용자를 만들고 돌려 봤다.

- 신청 → 인사팀 중간관리자 1차 승인 → 다른 최상급자 최종 승인 → `approved`. 결재자 이름 · 부서 · AI 등급이 남는다.
- 중간관리자 반려 → `rejected`. 1차 결재 전 철회 → `withdrawn`.
- 최상급자 회수 → `revoked`, `active_grants`에서 빠진다. 회수자 이름 · 부서 · 사유가 남는다.
- 아래 **25가지**를 DB가 거부한다.
  - 계정: 루트 아닌 사람의 계정 생성(최상급자 · 중간관리자), 루트 두 명, 만든 사람 없는 계정, 루트를 최상급자 아닌 역할로, 감사자 역할
  - 신청: 중간관리자의 신청, 날짜 없는 번호, 13월 번호, 2월 30일 번호, 제출한 내용 고치기
  - 결재: 1차를 건너뛴 최종 승인, 일반사용자 · 최상급자의 1차 결재, 같은 단계 두 번, 반려된 신청에 결재, 정지된 중간관리자의 결재, 결재 기록 수정 · 삭제
  - 상태: 1차 승인 뒤 철회, 반려된 신청 되살리기, 결재 없이 승인 완료로 바꾸기
  - 회수: 중간관리자의 회수, 승인 안 된 신청 회수, 두 번 회수, 회수 기록 삭제

## 5. 남은 질문

1. **세션 2일은 절대 만료** — 무활동 만료(예: 30분 안 쓰면 끊김)도 둘까?
2. **회수 범위** — 중간관리자는 아무 권한이나 회수할 수 있게 했다. 자기가 1차 승인한 건으로 한정해야 하나?
3. **사용 기간 만료** — 기간이 끝난 권한은 `active_grants`에서 빠지기만 한다 (기록은 `approved` 그대로). 만료를 따로 기록하거나 알려야 하나?
4. **루트가 떠나면?** 다른 최상급자에게 루트를 넘기는 절차(웹 밖)가 필요하나?
5. **루트 아닌 최상급자의 계정 권한** — 정지 · 비밀번호 초기화는 루트만인가?
6. **결재 이력 화면** — 중간관리자는 자기 결재만 보나, 전체를 보나?
7. **정책 데이터 · 정책 검토 · 질의 기록** — 권한 DB도 Log DB도 아니다. 어디에 두나?
8. **초기 루트 생성 방법** — 지금은 서버에서 실행하는 CLI(`make create-root`, 비밀번호는 화면 표시 없이 입력)로 만들었다. 다른 방법으로 정하면 바꾼다.
9. **AI 판정 입력** — 지금 판정은 신청자 · 신청 권한 · 현재 권한만 본다. 신청 사유 · 사용 기간도 보게 하려면 `review_chain` 프롬프트를 바꿔야 한다 (엔진).
10. **비밀번호 규칙** — 지금 12자 이상만 검사. 잠금은 5회 실패 → 15분.
